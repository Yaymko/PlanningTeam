# Team Load App — еженедельное планирование загрузки команды

Веб-приложение (Streamlit) для еженедельного планирования. Перед встречей загружается
экспорт тикетов с Agile-доски (.xlsx), и каждый сотрудник сам заходит в приложение,
выбирает себя, вписывает часы по своим тикетам на неделю и сохраняет. На планировании
видны сохранённые часы всей команды с перегрузами относительно нормы, и одной кнопкой
выгружается готовый отчёт на неделю в Excel с формулами и графиками.

## Что нужно для запуска

- Python 3.9+ (проверялось на 3.11–3.13)
- Windows / macOS / Linux — без разницы, зависимостей от ОС нет

## Разворачивание — Windows

1. Установите Python, если его ещё нет: https://www.python.org/downloads/
   При установке отметьте галочку **Add python.exe to PATH**.
2. Склонируйте репозиторий или скачайте архивом и распакуйте.
3. Откройте папку проекта и дважды кликните `run.bat`.
   Скрипт сам поставит зависимости (при первом запуске) и откроет приложение в браузере
   на `http://localhost:8501`.

Если `run.bat` ругается, что `python` не найден — установите Python и перезапустите
терминал/проводник, чтобы подхватился обновлённый PATH.

## Разворачивание — вручную (Windows / macOS / Linux)

```bash
# 1. Клонировать репозиторий
git clone <URL_РЕПОЗИТОРИЯ>
cd PlanningTeam

# 2. (рекомендуется) создать виртуальное окружение
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

# 3. Установить зависимости
pip install -r requirements.txt

# 4. Запустить приложение
streamlit run app.py
```

После запуска приложение откроется в браузере автоматически
(`http://localhost:8501`). Если не открылось — перейдите по ссылке из терминала вручную.

Остановить приложение — `Ctrl+C` в терминале, где оно запущено.

## Разворачивание — Visual Studio Code

Нужны Python (см. выше) и расширение **Python** от Microsoft в VS Code.

1. Распакуйте архив (или склонируйте репозиторий) и откройте папку проекта:
   **File → Open Folder**.
2. Откройте терминал: **Terminal → New Terminal** (`` Ctrl+` ``).
3. При первом запуске создайте окружение и поставьте зависимости:
   ```powershell
   python -m venv .venv
   .venv\Scripts\activate          # macOS/Linux: source .venv/bin/activate
   pip install -r requirements.txt
   ```
   Если VS Code предложит выбрать `.venv` как интерпретатор проекта, соглашайтесь.
4. Запустите приложение:
   ```powershell
   streamlit run app.py
   ```
   Откроется `http://localhost:8501`. Остановить — `Ctrl+C` в терминале.

В следующие разы достаточно `.venv\Scripts\activate` и `streamlit run app.py`.
Если в PowerShell активация запрещена политикой выполнения, выполните один раз
`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` или откройте терминал `cmd`.

## Общий доступ для команды

Чтобы сотрудники могли заполнять часы со своих компьютеров, приложение должно работать
на одной общей машине или сервере во внутренней сети, а не у каждого локально: часы
сохраняются в базу на той машине, где запущено приложение.

1. Разверните проект на общей машине (как выше).
2. Запустите так, чтобы приложение слушало сеть:
   - Windows: `run_server.bat`
   - вручную: `streamlit run app.py --server.address 0.0.0.0 --server.port 8501 --server.headless true`
3. Коллеги открывают `http://<имя-или-IP-машины>:8501`. Если не открывается, разрешите
   входящие подключения на порт 8501 в брандмауэре этой машины.

Данные хранятся в SQLite-файле `data/team_load.db` рядом с приложением (создаётся сам при
первом запуске). Другой путь задаётся переменной окружения `TEAM_LOAD_DB`, например
`TEAM_LOAD_DB=D:\planning\team_load.db`. Для резервной копии копируйте этот файл при остановленном приложении.
Перезапуск приложения часы не стирает.

Авторизации нет: любой, кто открыл приложение, может выбрать любого сотрудника. Поэтому
открывайте его только во внутренней сети, не в интернет.

## Запуск в Docker

Нужен Docker с Compose (Docker Desktop на Windows/macOS или Docker Engine на Linux).
Python ставить не нужно.

```bash
# в папке проекта
docker compose up -d --build
```

Приложение откроется на `http://localhost:8501`, коллеги заходят на
`http://<имя-или-IP-машины>:8501`. Контейнер сам поднимается после перезагрузки машины.

База с часами лежит в папке `data/` рядом с `docker-compose.yml` (она подключена в контейнер
как том), поэтому пересборка и обновление контейнера часы не стирают. Как перенести уже
сохранённые часы со старой машины — см. «Перенос сохранённых часов на другую машину».

- Посмотреть логи: `docker compose logs -f`
- Остановить: `docker compose down`
- Обновить после замены файлов проекта: `docker compose up -d --build`
- Другой порт: замените `"8501:8501"` в `docker-compose.yml`, например на `"8080:8501"`.

## Перенос сохранённых часов на другую машину

Все часы и загруженный план недели хранятся в одном файле `data/team_load.db`
(или по пути из `TEAM_LOAD_DB`). Чтобы перенести их:

1. На старой машине остановите приложение (`Ctrl+C` в окне `run.bat`/`run_server.bat`/терминала
   или `docker compose down`). Так последние записи гарантированно попадут в файл.
2. Скопируйте `data/team_load.db`. Если рядом остались `team_load.db-wal` и
   `team_load.db-shm`, скопируйте и их.
3. На новой машине тоже остановите приложение, удалите в `data/` всё, что начинается
   с `team_load.db` (это пустая база, созданная при первом запуске), и положите на их место
   скопированные файлы. При запуске в Docker это папка `data/` рядом с `docker-compose.yml`.
4. Запустите приложение — сохранённые часы и план недели будут на месте.

Так же делается и резервная копия: копируйте файл при остановленном приложении.

## Как пользоваться

1. **Загрузите план недели** (делает организатор планирования). Вкладка «Планирование» →
   «Загрузить выгрузку с доски на новую неделю» → выберите файл → «Сделать планом недели».
   Приложение ждёт экспорт тикетов с Agile-доски (.xlsx): листы «Обзор тикетов …»
   (справочно) + отдельный лист на каждого исполнителя с колонками
   `Тикет / Название / Колонка / Доска / Срок / В работе` и колонками-неделями вида
   `28.09–04.10 ч`. Если выгрузку обновили в течение недели, загрузите её повторно: уже
   введённые часы по тем же тикетам и неделям сохранятся.
2. **Каждый сотрудник заполняет свои часы до встречи.** Вкладка «Мои часы» → выберите
   себя → впишите часы по тикетам на неделю → «Сохранить». Строки «Доп. работа» — для
   задач, которых нет на доске: впишите название и часы. Новые строки добавляются кнопкой
   «+» внизу таблицы. Чтобы убрать тикет или работу, отметьте галочку «Удалить» в начале
   строки: строка сразу перестаёт учитываться в итогах и удаляется при сохранении. Если
   тикет удалён, а потом выгрузку с доски загрузили заново, он вернётся, потому что есть на доске. Там же норма часов в неделю
   (по умолчанию 40, уменьшите, если часть недели в отпуске). Под таблицей видно итого
   по неделям относительно нормы. Сохранять можно сколько угодно раз.
   По умолчанию видны только ближайшие 2 недели (текущая и следующая); остальные
   включаются переключателем «Показать все недели плана», их часы при сохранении не теряются.
3. **В конце недели сотрудник вписывает фактические часы.** Рядом с плановой колонкой
   каждой недели есть колонка «факт»: сколько часов реально ушло на тикет или доп. работу.
   Заполните её и нажмите «Сохранить». Факт переносится при повторной загрузке выгрузки так же,
   как план.
4. **На планировании** — вкладка «Планирование»: кто уже заполнил часы, а кто нет,
   сводная таблица по команде (по каждой неделе план и факт) с подсветкой перегруза (красный — выше нормы, зелёный — в
   пределах), графики загрузки по людям и неделям и «команда vs норма». При необходимости
   часы можно поправить прямо на встрече во вкладке «Мои часы», выбрав сотрудника.
5. **Отчёт на неделю** — кнопка «Сформировать Excel» внизу вкладки «Планирование»
   собирает файл из сохранённых часов всех сотрудников по всем неделям плана: лист на
   каждого (план, затем факт) и сводка по команде с формулами и графиками.

Недельные колонки читаются из заголовков файла динамически — при новой выгрузке с
другими датами ничего пересобирать не нужно, просто загрузите новый файл.

## Структура проекта

```
PlanningTeam/
├── app.py                      # UI: вкладки «Мои часы» и «Планирование», дашборд
├── core.py                     # чистая логика без Streamlit: разбор файла, сборка Excel-экспорта
├── storage.py                  # общее хранилище плана и часов (SQLite)
├── tests/                      # unit- и smoke-тесты (pytest)
├── requirements.txt            # зависимости приложения
├── requirements-dev.txt        # + зависимости для разработки (pytest, ruff)
├── pyproject.toml              # конфиг ruff
├── .github/workflows/ci.yml    # CI: линт + тесты на каждый push/PR
├── run.bat                     # быстрый запуск на Windows (ставит зависимости и стартует)
├── run_server.bat              # запуск на общей машине, доступно коллегам по сети
├── Dockerfile                  # образ приложения для запуска в Docker
├── docker-compose.yml          # запуск в Docker одной командой, база в ./data
└── README.md
```

## Разработка и CI

Логика разбора файла и сборки Excel-экспорта вынесена в `core.py` отдельно от
Streamlit-интерфейса в `app.py` — это позволяет тестировать её напрямую, без запуска
веб-сервера.

Локально, перед коммитом:

```bash
pip install -r requirements-dev.txt
ruff check .          # линт
pytest -q             # unit-тесты core.py + smoke-тест запуска app.py
```

На GitHub настроен workflow `.github/workflows/ci.yml` — при каждом push и pull request
в `main` он на Python 3.11 и 3.12 прогоняет линт (`ruff`), проверку компиляции и тесты.
Если какой-то шаг падает — PR будет помечен красным, это сигнал не мёржить, пока не
починено.

## Данные

Загружаемые `.xlsx`-файлы, сформированные экспорты и база `data/` не попадают в
репозиторий (исключены через `.gitignore`) — в них реальные данные по сотрудникам и тикетам.
